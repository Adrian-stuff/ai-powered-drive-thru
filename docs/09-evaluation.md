# 09 — Evaluation

Without this, "the new model is better" is an opinion, and provider swaps become
a matter of taste. The eval harness is what makes the swappable architecture
actually usable.

## The golden set

500 real orders from production, drawn to over-represent the hard cases:

| Slice | Share | Why |
| --- | --- | --- |
| Straightforward single-item | 15 % | The fast path must not regress |
| Combo with substitutions | 20 % | Most common real order shape |
| Mid-order corrections | 20 % | "actually, make that…" — where most systems fail |
| Heavy accents | 15 % | Segment accuracy is reported separately, never averaged away |
| High noise | 10 % | Rain, traffic, loud stereo |
| Children / multiple speakers | 10 % | Two voices ordering at once |
| Adversarial / off-topic | 10 % | Injection attempts, jokes, nonsense |

Each entry: input audio, the expected final `OrderState`, and acceptable
clarification behavior. Expected outputs are human-labeled and reviewed; a
golden set generated by a model measures agreement with that model, not truth.

## Metrics

**Order accuracy (primary).** Exact match on the final `OrderState` — SKU, size,
quantity, and modifiers. Partial credit per line item, but the headline number
is whole-order exact match, because a customer receiving 4 of 5 correct items
has received a wrong order.

**Containment.** Fraction completed without human takeover.

**Turn efficiency.** Turns per order. A system that gets there in nine turns is
failing even at 100 % accuracy — the car behind is waiting.

**Latency.** p50/p95 per stage, from `docs/04`.

**Over-confidence rate.** Turns with confidence > 0.9 that were wrong. The most
diagnostic number in the whole harness, and the one that catches R1 before
customers do.

**Cost per order.** Tokens, GPU seconds, or vendor spend, per profile.

## Running it

```
bun run eval --profile local --set golden-v3
bun run eval --profile hybrid --set golden-v3 --compare local
```

Reports per-slice, not just aggregate. A model that improves the average while
regressing on accented speech has made the product worse for real people at real
stores, and an aggregate number will hide that.

## Gates

| Context | Requirement |
| --- | --- |
| Every PR touching orchestration | No regression on a 50-order smoke set |
| Provider swap | Match or beat incumbent on accuracy *and* p95, on every slice |
| Model upgrade | Beat incumbent on accuracy; no slice regresses more than 2 pts |
| Prompt change | Full golden set; over-confidence rate must not increase |

## Shadow mode

Configured per port (`shadow:` in the profile), the runtime runs a candidate
provider in parallel on live traffic, discards its output, and records the diff
against the incumbent. This gives real-traffic evidence with zero customer risk,
and it is how a provider earns its way into a canary.

Shadow traffic is sampled (default 10 %) to bound GPU cost, and never runs when
the primary's breaker is open — the customer's turn always wins.

## The feedback loop

```
production sessions
  → low-confidence + handoff + 1 % random sample
    → weekly human review (~30 min)
      → new golden-set entries + new menu aliases
        → catalog rebuild, prompt fixes, threshold tuning
```

Half an hour of human review per week is the highest-leverage recurring activity
in the whole project. Most accuracy gains after launch come from here, not from
model upgrades — plan staffing for it rather than assuming it will happen.
